# Systems deliberately NOT ticked in a given runtime, or known gaps not yet closed.
#
# Format: <runtime>:<SystemMember>  meaning that runtime does not tick it while
# at least one other runtime does. Check with:
#
#     python tools/runtime_parity.py            # report
#     python tools/runtime_parity.py --strict    # exit 1 on NEW divergence
#     python tools/runtime_parity.py --record    # accept current state (loses these comments)
#
# --record rewrites this file and throws the reasoning away. Prefer editing it
# by hand so every line keeps saying WHY.

# ---------------------------------------------------------------------------
# Editor-only tooling. Not gameplay systems; a shipped game has no business
# running them.
# ---------------------------------------------------------------------------
desktop:CollabSystem
web:CollabSystem
desktop:FlashTimelineEditor
web:FlashTimelineEditor

# PlayMode is the editor's play-mode container, not a system. The players ARE
# the runtime, so there is nothing to contain.
desktop:PlayMode
web:PlayMode

# ---------------------------------------------------------------------------
# Engine plumbing driven differently per runtime, not per-frame gameplay
# systems. The tool matches on m_Thing.Update( and cannot tell these apart.
# ---------------------------------------------------------------------------
# The editor drives the world through PlayMode rather than calling
# World::Update itself.
editor:World
# The desktop and editor paths render through the frame loop; only web_main
# calls RenderSystem::Update directly.
desktop:RenderSystem
editor:RenderSystem

# ---------------------------------------------------------------------------
# Real platform limits on web. These are correct and will stay.
# ---------------------------------------------------------------------------
# A browser has no MIDI device in this build.
web:MIDIInput
# A browser has no UDP socket. The bindings still register on every platform so
# a script naming a Net_* symbol compiles, and web_main logs once at boot that
# the calls are inert.
web:NetworkSystem
# Web has its own post-process path (ApplyWebPostProcess); the PostProcessing
# object is #if'd out of the web registry entirely.
web:PostProcessing

# ---------------------------------------------------------------------------
# GAPS OF UNKNOWN INTENT. Found 2026-09-06 by the review that produced this
# tool. FlowerSystem and AudioReactiveSystem were two more of the same shape and
# are fixed; these are baselined so --strict guards against NEW drift while they
# are decided.
#
# Deliberately NOT labelled "bugs". I first wrote them up as unintended, then
# checked, and at least two look like decisions somebody already made without
# writing down why. Each needs a yes/no, not a fix applied on assumption.
# ---------------------------------------------------------------------------
# AudioGraphRuntime and AudioIndicators were here and are now CLOSED (both tick
# on web as of 2026-09-06). Marty confirmed the gaps were not intentional.
#
# Fluid stays, but as a SEQUENCED gap rather than an unknown. Marty asked for
# web fluid parity; the simulation would tick fine, but FluidRenderer.cpp is
# Vulkan-only (9 direct vk* call sites) and RenderSystem::SetFluidSimulation is
# a no-op stub on the web branch, so wiring the sim today costs frame time and
# draws nothing -- strictly worse than leaving it off. It lands with the WebGPU
# fluid render path, hardening list item 18.
web:FluidSimulation
web:FluidTerrainCoupling
# PARTLY a false positive of this tool, and worth reading before acting on it.
# Per-sprite parallax works in all three runtimes: they all call the STATIC
# ParallaxSystem::ApplyParallaxLayers, which this tool cannot see because it
# only matches m_Thing.Update(. What the players genuinely lack is the
# ParallaxMachineComponent backdrop path (the instance Update + Render), so a
# scene authored with a ParallaxMachine shows its layers in the editor and not
# in the shipped game. Narrower than "parallax is broken in the player", and
# fixing it means wiring Render into each player's 2D pass, not just a tick.
desktop:ParallaxSystem
web:ParallaxSystem
