## 1. ECS & World System

### CRITICAL

**ECS-C1. Race condition in lock-free component access**
- **File:** `Engine/include/Enjin/ECS/World.h:105-119`
- **Issue:** `GetComponent()` and `HasComponent()` access `m_ComponentStorages` (unguarded `unordered_map`) without acquiring `m_Mutex`. Concurrent modification via `AddComponent`/`RemoveComponent` causes undefined behavior.
- **Impact:** Data race, iterator invalidation, use-after-free of storage pointers.
- **Note:** This is the same as prior TH-1. Still open.

**ECS-C2. Dangling pointer risk in View iterator**
- **File:** `Engine/include/Enjin/ECS/View.h:137-145`
- **Issue:** If a component storage is cleared/destroyed between View construction and iteration, `SmallestEntities()` returns a reference to destroyed vector data.
- **Impact:** Segfault or undefined behavior during iteration.

**ECS-C3. Use-after-free in RebuildNameCache**
- **File:** `Engine/src/ECS/World.cpp:126-147`
- **Issue:** Iterates `GetEntitiesWithComponent<NameComponent>()` and calls `GetComponent()` without holding a lock. Another thread modifying storage causes the returned reference to point to reallocated memory.
- **Impact:** Heap buffer overflow, use-after-free.

**ECS-C4. Unguarded hierarchy modification**
- **File:** `Engine/include/Enjin/ECS/Components/Hierarchy.h:22-81`
- **Issue:** `SetParent()` performs multiple reads/writes to parent/children components without locking. Concurrent calls corrupt parent/child relationships.
- **Impact:** Broken hierarchy trees, orphaned entities.

### HIGH

**ECS-H1. Stale cached storage pointers in RenderSystem**
- **File:** `Engine/src/ECS/Systems/RenderSystem.cpp:2506-3081`
- **Issue:** Caches raw `ComponentStorage<T>*` pointers. `World::Clear()` destroys all storages, leaving cached pointers dangling.

**ECS-H2. Iterator invalidation during entity destruction**
- **File:** `Engine/src/ECS/Systems/ControllerSystem.cpp:96-195`
- **Issue:** Loops iterate entity vectors while operations may destroy entities mid-iteration. `IsValid()` checks mitigate but pattern is fragile.

**ECS-H3. Missing lock in InvalidateNameCache**
- **File:** `Engine/include/Enjin/ECS/World.h:223`
- **Issue:** Sets `m_NameCacheDirty = true` without mutex. No happens-before relationship on weak-memory architectures (ARM).

## 2. Vulkan Renderer

### CRITICAL

**VK-C1. Missing vkBindBufferMemory error check**
- **File:** `Engine/src/Renderer/Vulkan/VulkanImage.cpp:179`
- **Issue:** `vkBindBufferMemory()` for staging buffer does not check return value. If binding fails, subsequent buffer use causes undefined behavior.
- **Impact:** Silent memory binding failure, GPU memory corruption or crashes.

**VK-C2. Overly permissive pipeline barriers**
- **File:** `Engine/src/Renderer/Vulkan/VulkanImage.cpp:432-433`
- **Issue:** Fallback case uses `VK_PIPELINE_STAGE_ALL_COMMANDS_BIT` for both source and destination. Serializes ALL GPU operations.
- **Impact:** Massive performance penalty. Masks layout transition bugs.
- **Note:** Same as prior MEDIUM finding. Elevated to CRITICAL due to perf + correctness masking.

**VK-C3. Missing vkQueueSubmit error check**
- **File:** `Engine/src/Renderer/Vulkan/VulkanImage.cpp:311`
- **Issue:** `vkQueueSubmit()` result not checked during image upload. Failed submission followed by `vkQueueWaitIdle()` and staging buffer destruction causes use-after-free.
- **Impact:** Incomplete image transfer, potential GPU hangs.

## Systemic Patterns

### Pattern 1: Thread Safety is the #1 Risk

17 of 24 CRITICAL findings involve thread safety or race conditions. The engine's threading model assumes single-threaded access in many subsystems but doesn't enforce it. Key hotspots:
- ECS World component access (ECS-C1, ECS-C3, ECS-C4)
- PlayMode state transitions (ED-C2)
- Script instruction counter (ED-C3)
- Physics filter data (PH-H4)
- Audio processing (AUD-H2)

**Recommendation:** Adopt a formal threading policy. Either:
1. Document and enforce single-threaded access with debug assertions, OR
2. Add proper synchronization (shared_mutex for read-heavy paths)

### Pattern 2: Missing Bounds Validation at Deserialization Boundaries

Scene files, prefabs, assets, and network packets are trust boundaries. Multiple findings show array access without size checks, integer overflow in size calculations, and missing path validation.

**Key files needing hardening:**
- `Prefab.cpp` (SEC-C2, SEC-M3)
- `AssimpLoader.cpp` (SEC-H1, SEC-H2)
- `NetworkSystem.cpp` (SEC-H3, SEC-H4, SEC-M9)

### Pattern 3: Third-Party Dependencies Are Unpatched

- **cgltf.h** — `strcpy` buffer overflow (SEC-C1, open since April 2026)
- **stb_image_write.h** — unsafe `sprintf` (SEC-M7)
- Assimp library — integer overflow paths (SEC-H1)

**Recommendation:** Fork and patch cgltf.h locally. Pin stb versions and apply known patches.

### Pattern 4: Error Recovery Is Incomplete

Vulkan API calls frequently lack error checks (VK-C1, VK-C3). When errors are checked, recovery is often partial — resources are leaked or left in invalid states. The fence-before-submit pattern (VK-H2) is particularly dangerous.

### Pattern 5: Resource Lifecycle Management

Multiple subsystems cache raw pointers that can become dangling:
- ECS storage pointers in RenderSystem (ECS-H1)
- Physics constraint pointers (PH-C3)
- Script context instruction counters (ED-H4)
- Visual Script global system pointers (ED-C1)

**Recommendation:** Consider reference-counted handles or invalidation callbacks.
