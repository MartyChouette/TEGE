Renderer Backend Abstraction

Why TEGE is decoupling from Vulkan — and what that means for every platform

The Problem

Before: Direct Vulkan Coupling

Every line of rendering code in RenderSystem.cpp (9,854 lines) directly calls Vulkan functions. The renderer is Vulkan.

// This is what RenderSystem looks like today — raw Vulkan everywhere
vkCmdBindVertexBuffers(commandBuffer, 0, 1, &vertexBuffer, offsets);
vkCmdBindIndexBuffer(commandBuffer, indexBuffer, 0, VK_INDEX_TYPE_UINT32);
vkCmdBindDescriptorSets(commandBuffer, VK_PIPELINE_BIND_POINT_GRAPHICS,
    pipeline->GetLayout(), 0, 1, &descriptorSet, 1, &dynamicOffset);
vkCmdPushConstants(commandBuffer, layout, VK_SHADER_STAGE_ALL, 0, 128, &pushData);
vkCmdDrawIndexed(commandBuffer, indexCount, 1, 0, 0, 0);

This means RenderSystem only works on Vulkan. It's completely excluded from WebGPU builds. The web player had to rewrite rendering from scratch — and that rewrite has ~20% of the features.

The Solution

After: Backend Abstraction

RenderSystem talks to an abstract interface. The interface has implementations for Vulkan, WebGPU, and (future) Metal. Same game logic, same rendering code, different GPU APIs underneath.

// This is what RenderSystem will look like — backend-agnostic
encoder->SetVertexBuffer(0, vertexBufferHandle, 0);
encoder->SetIndexBuffer(indexBufferHandle, GPUIndexFormat::Uint32, 0);
encoder->SetBindGroup(0, viewBindGroup, 1, &dynamicOffset);
encoder->SetInlineConstants(0, 128, &pushData);
encoder->DrawIndexed(indexCount, 1, 0, 0, 0);

The exact same code runs on Windows (Vulkan), browser (WebGPU), and Mac (Metal). No per-platform rewrites.

Concrete Example: Creating a Buffer

BEFORE — Vulkan only

// Must know you're on Vulkan
auto* ctx = m_Renderer->GetContext();
auto buffer = std::make_unique<VulkanBuffer>(ctx);
buffer->Create(size, BufferUsage::Vertex, false);
buffer->UploadData(vertices, vertexCount * sizeof(Vertex));

AFTER — Any backend

// Works on Vulkan, WebGPU, Metal — identical code
GPUBufferDesc desc;
desc.size = vertexCount * sizeof(Vertex);
desc.usage = GPUBufferUsage::Vertex;
auto handle = m_Renderer->GetBufferManager()
    ->CreateBufferWithData(desc, vertices);

The GPUBufferHandle is a typed opaque ID. Vulkan resolves it to a VkBuffer. WebGPU resolves it to a WGPUBuffer. Metal will resolve it to an id<MTLBuffer>. RenderSystem never knows or cares.

The Push Constants Problem

Vulkan has push constants — 128 bytes of per-draw data uploaded with zero overhead. WebGPU and Metal don't have this feature.

The abstraction solves this with SetInlineConstants():

  • Vulkan maps to vkCmdPushConstants — native, zero cost
  • WebGPU maps to a reserved uniform buffer upload — small cost, but correct
  • Metal maps to setBytes — native, near-zero cost

RenderSystem calls encoder->SetInlineConstants(0, 128, &data) everywhere. Each backend does the right thing.

Feature Gating

Not every backend supports every feature. GPUCapabilities tells RenderSystem what's available:

FeatureVulkanWebGPUMetal
Push constantsYesNo (UBO fallback)No (setBytes fallback)
Compute shadersYesYesYes
Ray tracingYes (VK_KHR_ray_tracing)NoYes (MPS)
Multi-draw indirectYesNoYes
Async compute queueYesNoYes
Mesh shadersYes (ext)NoYes (Metal 3)
Bindless resourcesYesNoYes (argument buffers)
// RenderSystem checks capabilities before using advanced features
auto caps = m_Renderer->GetGPUCapabilities();

if (caps.CanDoGPUCulling()) {
    PerformGPUCulling();    // Vulkan + Metal: compute shader culling
} else {
    PerformCPUCulling();    // WebGPU: CPU-side frustum test
}

if (caps.hasRayTracing) {
    DispatchRTShadows();    // Vulkan + Metal only
}
